# macOS 连续播放爆鸣及后续错位排查

排查基线：`dev` 的 `da90dfff`；分支 `codex/investigate-audio-pop-drift`。
报告场景：macOS、内置扬声器、1 倍速正常连续播放，偶发爆鸣后音频与音符错位。
首轮仅静态排查；随后用户实机复现并提供爆鸣秒数，已核对应用和系统日志。
尚未修改播放实现。
用户确认运行仓库构建版本；从应用偏好定位到 God Save The Girls，检查其现存日志，
仅发现 Runtime 和 Export 日志，没有 Audio 日志，无法用历史记录确认爆鸣时刻的音频进度。

## 已确认的代码事实

1. `BassPreviewAudioBackend_EngineInit.cpp::initializeAudioEngine` 对主混音器设置
   `BASS_ATTRIB_BUFFER = 0`，并启用 8 个混音线程。前者关闭通道的播放预缓冲，
   不等于设备本身没有缓冲。[BASS 官方说明](https://www.un4seen.com/doc/bass/BASS_ATTRIB_BUFFER.html)
   明确指出：此模式在最终混音需要数据时才生产数据，DSP/FX 和 mixtime sync
   超时会中断同一设备上的输出。8 线程是否增加本机调度开销尚未验证。
2. `MainWindow.TimelinePlayback.cpp::currentPreviewAuthoritativeAudioClockSecond`
   在播放中返回 `qtPreviewStartSecond_ + qtPreviewElapsed_ * rate`，不会跟随音频停顿。
3. `BassPreviewAudioBackend_EventDrain.cpp::anchorSfxScheduler` 将音效绑定到主混音器
   `BASS_POS_DECODE`；正常播放由 `BASS_SYNC_POS | BASS_SYNC_MIXTIME` 回调触发。
   `drainEvents` 在此调度器启用时直接返回，避免 GUI 重复播放音效。
4. `BassPreviewAudioBackend_Transport.cpp::syncBackgroundTrack` 只处理待启动 BGM
   和状态日志，没有比较实际位置后纠偏的逻辑。因此，如果音频处理进度落后于
   系统计时器，持续错位有明确的代码解释；尚不能证明此次爆鸣就是这种情况。
5. `Sample::create` 将源文件整体读入内存，随后创建解码流。不能直接把连续播放
   的卡顿归因于每次回调读取音乐文件；压缩音频解码仍在播放链路中。

## 现有观测的局限

- `bass_status` 的 `bgm_delta_ms` 可用于对比爆鸣前后的偏移变化，但 BGM 位置来自
  最近一次健康采样，并非与画面时间同时读取；应观察持续台阶，不能拿单行的
  非零值断言失步。`syncBackgroundTrack` 给状态函数传入两份相同时间，故该路径的
  `drift_ms` 恒为零，不能作为同步正常的证据。
- `PreviewAudioWorker::sampleHealth` 用 `snapshot.authoritativeSecond` 限制周期日志
  并计算 stall 时长。BASS 的该值来自 `lastAuthoritativeSecond`，普通连续播放的
  sync/drain 路径不推进它，可能使健康日志只输出起始行，stall 时长也不可信。
- 健康检测轮询 `BASS_ACTIVE_STALLED`，未记录每次设备输出回调耗时；短暂的中断
  可能没有被采到。没有 stall 行不能排除中断。
- 音效回调持有 `schedulerMutex_`，执行音效定位/启动以及下一事件注册；debug
  模式还格式化并入队日志。日志正常情况下异步写盘，不能将其描述为回调逐条
  同步写盘。回调与锁的实际耗时仍需测量。
- 旧 `AUDIO_CLOCK_DESYNC_AUDIT_ZH.md` 中“没有设备监听”等结论已不适用于当前代码；
  当前已有设备变更暂停处理，不能直接套用旧报告认定根因。

## 当前假设与验证判据

优先假设：零预缓冲路径发生处理超时/输出中断，随后音频进度与系统计时器分离，
而播放路径没有重新对齐。它解释两段症状，但爆鸣的具体触发点仍待证实。

1. 确认实际运行的 app 版本、谱面目录及音频日志，以 `--debug` 连续播放建立基线。
2. 爆鸣时记下墙上时间及谱面秒数，保留之后约 10 秒连续播放，再暂停一次。
   同时记录 BGM 与打击音是否仍彼此对齐，及暂停续播是否恢复。
3. 检查 `bass_status` 的偏移是否出现持续台阶，结合 `bass_stall`、`bass_err`、
   设备变化和播放事务日志排除设备切换、隐式 seek、重新起播等路径。
4. 若现有日志不足，先修正诊断时基并记录实际混音器/BGM/系统时间的同批快照，
   实时回调仅写入有界计数或耗时数据，由 worker 输出，避免诊断增加回调负担。
5. 在可复现场景上比较当前零预缓冲与有限预缓冲。若改善，还需同时验证起播、
   暂停续播、seek、音效和画面延迟；不能单纯增加缓冲后宣称问题解决。

## 用户协同复现结果

用户以仓库构建版本开启 `--debug`，报告在播放进度 1:09～1:10 爆鸣。
本次为 1 倍速、BASS tempo 模式、背景图片，无视频；从 0 秒连续播放到约 78.36 秒手动暂停。

### 系统证据：音频输出周期超时

2026-09-16 13:47:38.532（UTC+8），MiaCode 进程的 CoreAudio 日志明确记录：

```text
HALC_ProxyIOContext::IOWorkLoop: skipping cycle due to overload
```

紧接着 13:47:38.542 的 CoreAudio 分析记录将事件归于 MiaCode，输出为内置扬声器：

- `HAL_client_IO_duration = 12355666`，约 12.36 ms。
- `io_cycle_budget = 10645833`，约 10.65 ms。
- `smallest_buffer_frame_size = 480`，`sample_rate = 48000`。
- `io_page_faults = 0`。

应用在 13:46:28.803 提交播放，因此该系统事件对应约 **69.729 秒**，落在用户报告范围内。
这确认了本次故障对应一次 CoreAudio 输出周期超时/跳过，不再仅是静态猜测。
系统日志没有提供 C++ 调用栈，无法据此判定时间具体消耗在解码、混音、线程唤醒还是锁等待。

### 应用证据：音频事件时基出现持续台阶

用每条 `bass_sfx_mixer_trigger` 的日志时间减去播放提交时间，再减去该事件的
`group_second`，观察相对残差（仅为回调日志时刻，不等于扬声器实际出声时刻）：

| 谱面区间 | 事件数 | 残差中位数 |
| --- | ---: | ---: |
| 65～69 s | 26 | -7.69 ms |
| 69.8～71 s | 6 | +7.57 ms |
| 71～75 s | 23 | +7.08 ms |
| 75～79 s | 27 | +6.49 ms |

最后一个台阶前事件为 69.529412 秒，下一事件为 69.865686 秒。
系统 overload 位于两者之间；台阶约 **15 ms**，直到手动暂停前均未回到原基线。
正常回调的周期量化和日志开销会引入抖动，所以不能把 15 ms 当作精确的设备输出延迟。
捕获期间没有应用记录的 seek、变速、设备切换或重新起播；没有 `bass_err` / stall 行。

### 避免误读 BGM 日志

69.65 秒的 `bgm_delta_ms=450.464` **不能证明音乐落后 450 ms**。
健康采样每秒一次，状态行将旧的 BGM 位置与当前系统时间相减，且没有输出采样年龄。
其约 0～1 秒的偏差包含观测时间差。本轮实际可确认的是上述回调时基台阶。
健康日志也确实仅出现起播前一行 `txn=0 second=0`，印证限频时基不推进的问题。

### 定位结论与修复边界

故障链已有实机证据支持：**CoreAudio 超时跳过输出周期 → 音频事件进度相对系统时间
留下持续台阶 → 当前同步路径不纠偏**。零预缓冲使解码/混音及回调工作直接面对输出期限，
是首要改进候选，但尚未通过 A/B 验证它是否足以消除超时。

后续修复需同时处理实时输出负载/缓冲和中断后的时间对齐；不宜只用增大缓冲掩盖问题。
若要继续细分超时成本，应先完善低干扰的耗时观测，再用相同场景验证。
本轮无播放代码变更、无构建或测试、无提交或推送。

## 修复实现

后续用户授权继续修复后，在同一分支实现：

- 主混音器由 8 个混音线程改为 1 个，避免每个短输出周期都分发并等待多个线程。
  保留现有零预缓冲，避免凭空增加起播、暂停及 seek 尾音延迟；是否进一步需要
  有限预缓冲，留待此版本实机结果决定。
- BASS worker 采集主混音器的 **playback position**，以音效调度锚点映射到谱面秒数，
  连同采样时的单调时钟和倍率发布到快照。GUI 不直接进入 BASS。
- 画面、时间轴及编辑器跟随统一读取插值后的音频时钟。连续段保持单调，遇到
  向后校正短暂等待音频追上；seek 的 generation 及变速可开始新的时间段。
  worker 超过 100 ms 未更新时停止外推，旧 generation/asset/transaction 或倍率
  不匹配的快照不能接管时钟。无音频时钟的兼容后端继续使用原 fallback。
- 健康日志限频和 stall 时长改用单调时钟；状态日志即时采样，消除旧 BGM 采样
  造成的假偏移，并增加 `clock_valid` / `clock_second` 供复测。
- 离线导出仍使用逐帧时间，不读取实时音频设备时钟。

本机无声解码对照（14 路 PCM 输入，经逐样本 resampler 进入主 mixer，每块 480 帧；
两轮 8/1 线程交替，构建期间执行，非真实歌曲/设备回调）：8 线程耗时中位数
0.082～0.087 ms，P99 0.90～1.58 ms；1 线程中位数 0.032～0.033 ms，
P99 0.21～0.26 ms。该结果支持减少线程协调成本，不能证明实机爆鸣已消除。

回归用例覆盖 15 ms 丢时后的校正、不倒退、无更新时有限外推、向后 seek、变速、
负时间预卷，以及原生时钟快照跨 worker 边界。

验证：完整 Release 开发目标构建通过；音频、worker 协议/队列/屏障、设备变更、
retained transport、时钟策略及导出音频计划相关的 13 项 CTest 全部通过。
`git diff --check` 通过。macOS 内置扬声器实机复测后，报告者反馈“应该是好了”；尚未完成 Windows 构建或实机复测。
没有修改谱面偏移值；单线程性能对照只覆盖本机，不能据此认定所有平台均有相同收益。
